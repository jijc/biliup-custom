# biliup-custom 设计说明

日期：2026-08-24

## 1. 目标

在不改变 biliup 数据库结构、主播配置格式、投稿模板格式和上传逻辑的前提下，为官方 biliup 增加一层尽可能薄的录像路径能力，并保持长期可升级、可回退、可最终完全回归官方镜像。

长期目标：

- 录像直接写入 NAS 的 `/volume1/Biliup`，容器内挂载为 `/recordings`。
- 录像目录结构为：`/recordings/{主播名称}/{逻辑日期}/文件名.flv`。
- 逻辑日期以每天 04:00 为换日边界：00:00-03:59 归前一天，04:00 起归当天。
- 文件名保持：`[%Y年%m月%d日-%H时%M分%S秒][{streamer}][{title}]`。
- 45 分钟分段继续由 biliup 原生能力负责。
- 分段文件从创建开始就位于最终目录；不使用 `mv`、不等待整场直播结束。
- 自动投稿、重试、分段事件、后处理等继续使用 biliup 官方实现。
- 官方更新时自动跟随并构建自定义镜像。
- 如果官方未来原生支持等价能力，应优先停用补丁并回归官方镜像。

## 2. 非目标

本项目不：

- 修改 biliup 的 SQLite 数据库 schema。
- 修改 B 站账号登录数据格式。
- 修改主播/投稿模板的数据结构。
- 重写录制器、上传器、重试逻辑或 WebUI。
- 自己实现文件移动守护进程。
- 自己维护完整的 biliup fork。

## 3. 当前上游约束

当前 biliup 的 `Recorder::filename_template()` 会调用 `sanitize_filename()`，而该函数会把 `/` 和 `\\` 替换为 `_`，因此目录分隔符无法通过文件名模板保留。

另一方面，stream-gears 底层的 `LifecycleFile::create()` 已经会对目标文件的父目录执行 `create_dir_all(parent)`。因此上游已经具备“创建多级父目录”的底层能力，缺失的是“安全地保留目录结构并分别清洗每个路径组件”的模板层能力。

当前 server 侧下载配置把 `output_dir` 设为当前目录 `.`，因此自定义方案需要让最终路径由模板本身生成，并保证其位于 `/recordings` 下。

## 4. 推荐架构

采用“官方源码 + 小补丁 + 自动构建”的方式，而不是长期 fork。

数据流：

```text
biliup/biliup master
      ↓
GitHub Actions 定时检测上游 commit
      ↓
拉取指定上游 commit
      ↓
应用 biliup-custom 小补丁
      ↓
运行补丁测试/构建测试
      ↓
构建 linux/amd64 + linux/arm64 镜像
      ↓
ghcr.io/jijc/biliup-custom:latest
      ↓
群晖 Container Manager / 后续自动更新器
```

NAS 挂载保持数据与录像分离：

```yaml
volumes:
  - ./data:/opt
  - /volume1/Biliup:/recordings
```

其中：

- `/opt`：biliup 数据库、登录状态、WebUI 配置等。
- `/recordings`：实际录像文件。

## 5. 路径模板设计

自定义版新增一个兼容现有 `filename_prefix` 的目录模板能力，不改变已有占位符语义。

推荐长期模板：

```text
/recordings/{streamer}/{record_date}/[%Y年%m月%d日-%H时%M分%S秒][{streamer}][{title}]
```

新增占位符：

- `{record_date}`：按本地时区计算的逻辑日期，当前时间减 4 小时后格式化为 `%Y-%m-%d`。

已有占位符继续保持：

- `{streamer}`：主播名称。
- `{title}`：直播标题。
- `{url}`：直播间地址。
- `%Y/%m/%d/%H/%M/%S` 等：继续由 chrono/strftime 处理。

示例：

```text
/recordings/测试录播-老姨/2026-08-24/[2026年08月24日-15时35分25秒][测试录播-老姨][六耳猕猴合点宝宝~].flv
```

若时间为 2026-08-25 02:10，则目录仍为：

```text
/recordings/测试录播-老姨/2026-08-24/
```

但文件名中的真实时间仍为 2026年08月25日-02时10分xx秒。

## 6. 安全清洗规则

不能简单取消文件名清洗，否则直播标题中可能出现非法字符或路径穿越风险。

因此补丁应把“清洗整个字符串”改成“路径感知清洗”：

1. 保留合法的目录分隔结构。
2. 对每一个路径组件单独清洗 `: * ? \" < > |`、控制字符等非法字符。
3. 主播名和标题中的 `/`、`\\` 不能成为新目录，必须在对应占位符展开后按组件清洗为 `_`。
4. 拒绝或消解 `.`、`..` 等路径穿越组件。
5. 只允许最终路径落在配置的 `/recordings` 根目录下。

这样既能保留我们主动写入模板的 `/`，又不会让直播标题中的 `/` 意外创建额外目录。

## 7. 兼容与回退策略

### 7.1 数据兼容

不修改数据库 schema，因此同一个 `/opt/data/data.sqlite3` 可继续被官方 biliup 使用。

### 7.2 镜像回退

群晖只需要把镜像从：

```text
ghcr.io/jijc/biliup-custom:latest
```

改回：

```text
ghcr.io/biliup/caution:latest
```

即可恢复官方镜像。

已有录像目录不会受影响；官方版只是不会继续使用自定义目录模板能力。

### 7.3 官方出现同类功能

自动同步流程每次构建前应做“上游能力探测”。

若检测到官方已经存在等价的路径模板/输出目录能力：

- 不自动猜测迁移参数。
- 停止发布新的补丁版 `latest`。
- 自动在 `jijc/biliup-custom` 创建 Issue，提示“上游可能已原生支持，请迁移到官方功能”。
- 保留最后一个已验证可用的自定义镜像。
- 人工确认一次配置映射后，删除补丁并切回官方镜像。

目标是最终退出自定义层，而不是永久维护它。

## 8. 自动更新策略

GitHub Actions 包含三类触发：

1. `workflow_dispatch`：手动触发。
2. `schedule`：定时检查官方 `master`。
3. 本仓库配置变化：重新构建。

状态文件记录最近成功构建的上游 commit SHA。

只有在以下任一情况发生时才构建：

- 上游 commit SHA 发生变化。
- 本仓库补丁/构建逻辑发生变化。
- 手工触发。

发布标签：

- `latest`：最近一次成功验证的版本。
- `upstream-<short_sha>`：对应具体上游 commit 的可追溯版本。

只有完整测试和镜像构建成功后才更新 `latest`。失败时旧 `latest` 保持不变。

## 9. 失败通知

当出现以下情况时，GitHub Actions 自动创建或更新一个 Issue：

- 补丁无法应用。
- 路径相关测试失败。
- Docker 镜像构建失败。
- 检测到官方可能已经具备同类能力。

成功恢复后，可自动关闭“同步失败”类 Issue，避免重复告警。

GitHub 是否进一步发送邮件/手机通知，由用户自己的 GitHub 通知设置决定。

## 10. 群晖自动更新

GitHub 镜像自动更新和 NAS 容器自动更新分开设计。

第一阶段完成自定义镜像后，群晖仍可手工“重新构建/拉取”进行验证。

验证稳定后，再增加只针对 biliup-custom 的自动更新器（例如 Watchtower 或等价方案）：

```text
GHCR latest 更新
  ↓
群晖检测新镜像
  ↓
拉取
  ↓
重建 biliup 容器
```

自动更新器不应管理 NAS 上其他容器。

## 11. 测试设计

补丁至少需要覆盖：

- `{streamer}` 正常生成主播目录。
- `{record_date}` 在 04:00 前后正确换日。
- 文件名中的时间保持真实时间，不跟随逻辑日期回退。
- 主播名包含 `/` 时不能创建额外目录。
- 标题包含 `/`、`:`、`?` 等字符时正确清洗。
- `..` 不能逃逸 `/recordings`。
- 目标多级目录不存在时能自动创建。
- 45 分钟分段后的每一个新文件直接出现在相同主播/逻辑日期目录。
- 不关联投稿模板时可正常录制。
- 关联投稿模板时分段文件路径仍能被原生上传流程读取。

## 12. 实施边界

首版只实现本设计明确需要的能力：

- `/recordings` 根路径。
- `{streamer}` 目录。
- `{record_date}` 04:00 换日。
- 原文件名模板。
- 自动同步、构建、失败提醒。

不在首版加入 WebUI 新字段、复杂目录 DSL、自动清理录像、自动调整 B 站投稿策略等额外功能。

## 13. 完成标准

当以下条件全部满足时，首版完成：

1. GitHub Actions 能基于官方最新 master 自动构建自定义镜像。
2. NAS 使用自定义镜像后，数据库和原配置可继续使用。
3. 一场直播开始后，`.part` 文件直接创建在 `/volume1/Biliup/主播/逻辑日期/`。
4. 分段完成后原地变成 `.flv`，不需要 `mv`。
5. 文件名符合预期格式。
6. 04:00 换日规则正确。
7. 官方更新后可自动产生新的可追溯镜像。
8. 同步失败不会覆盖当前稳定 `latest`，并能产生 GitHub Issue 提示。
9. 切回官方镜像时不需要迁移数据库。
